# Windfall: UK wind forecast monitor

A web app for a UK energy utility's day-ahead trading desk. It shows the national wind generation forecast the desk would have had when buying power on the day-ahead market, compares it with what wind actually produced, and measures how accurate those forecasts are.

Scope: national wind generation for delivery days covered by purchase decisions made in January 2026, using Elexon BMRS data only.

- **Live app:** https://x7kq2-xn99.vercel.app
- **API docs (generated by FastAPI):** https://x7kq2.vercel.app/docs
- **Video walkthrough:** [YOUTUBE URL]

## What it does

| Page | Purpose |
|---|---|
| **Forecast** | Actual vs forecast wind generation for every hour, with a likely range (P10 to P90) around the forecast. Key figures: typical error, bias, and the margin that covered 9 in 10 hours. |
| **Accuracy** | MAE, RMSE, bias and worst hour. Error vs forecast lead time (0 to 48 h), error by hour of day, error distribution, and a daily table with filter and CSV export. |
| **Method** | Data sources, which forecast is used, how accuracy is measured, and the assumptions. |

Two ways to pick the forecast for each hour:

- **Decision view (default):** the newest forecast published at or before 11:00 UK time on the day before delivery. This is the forecast the desk had when the day-ahead auction closed.
- **Horizon view:** the newest forecast published at least N hours before delivery (slider, 0 to 48 h). Shows how accuracy improves closer to delivery.

The view settings live in the URL (for example `/accuracy?mode=horizon&horizon=12`), so a link reproduces the same view.

## Data

| Dataset | Used fields | Notes |
|---|---|---|
| [FUELHH](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/FUELHH/stream) (actual generation) | `startTime`, `generation`, filtered to `fuelType = "WIND"` | Half-hourly |
| [WINDFOR](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/WINDFOR/stream) (wind forecast) | `publishTime`, `startTime`, `generation` | Hourly values, several forecast runs per day |

Ranges downloaded:

- Actuals: settlement dates 1 Jan to 1 Feb 2026.
- Forecasts: published 30 Dec 2025 to 31 Jan 2026. The extra days give enough history for the 48 h horizon view on the first delivery days.

The data is downloaded once by `backend/scripts/ingest.py` into `backend/data/wind.db` (SQLite, about 2 MB, committed to the repo). The deployed app never calls Elexon, so it keeps working if Elexon is slow or down.

## Architecture

```
Browser (React)
   │  GET /api/series, /api/metrics, /api/metrics/by-horizon
   ▼
FastAPI backend
   ├─ routes/api.py              HTTP layer: query params, validation, JSON
   ├─ services/forecast_select.py  picks one forecast per hour (core logic)
   ├─ services/metrics.py          MAE, RMSE, bias, percentiles, breakdowns
   └─ data/wind.db                 SQLite, loaded once into pandas and cached
```

- **Separation of concerns:** routes only translate HTTP to function calls. All logic is in pure functions (DataFrame in, DataFrame or dict out), which makes it easy to test.
- **Dependency injection:** routes get their data through `Depends(get_data)`, so API tests swap in a small fake dataset.
- **Validation:** query parameters are typed (`mode` must be `decision` or `horizon`, `horizon` must be 0 to 48), so bad input returns a clear 400 or 422 error.
- **Time zones:** the 11:00 cutoff is calculated in UK local time, so it stays correct across clock changes.

## Running locally

### Option 1: Docker (one command)

Requires Docker Desktop.

```bash
docker compose up --build
```

Open http://localhost:3000. The API is at http://localhost:8000 and its docs at http://localhost:8000/docs.

### Option 2: without Docker (for development)

Requires Python 3.12 and Node 20 or later.

**Backend**

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python scripts/ingest.py           # only needed if data/wind.db is missing
uvicorn app.main:app --reload
```

**Frontend** (in a second terminal)

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. The dev server forwards `/api` requests to the backend on port 8000.

### Tests

```bash
cd backend
pytest -v
```

The tests cover the forecast selection rules (cutoff boundary, midnight delivery, clock changes, horizon mode, forecasts published after their target time), the metric calculations (checked against hand-worked numbers), and the API (validation errors, response shape, and that a forecast published after the cutoff is never used).

| `ALLOWED_ORIGINS` | backend | Comma-separated origins allowed by CORS, for example the Vercel URL | `*` |

## Deployment

- **Frontend:** Vercel, project root `frontend`, framework Vite, environment variable `VITE_API_URL` set to the backend URL.
- **Backend:** Vercel (Python runtime, FastAPI detected from `app/main.py`), project root `backend`, environment variable `ALLOWED_ORIGINS` set to the frontend URL. `backend/Dockerfile` is used for local Docker runs.

## Assumptions and limitations

1. **Decision cutoff is 11:00 UK time on the day before delivery**, the usual close of the GB day-ahead auction. It is one constant (`DECISION_CUTOFF_HOUR`) and easy to change.
2. **Only on-the-hour slots are compared.** Forecasts are hourly and actuals half-hourly, so the :30 actuals are not used in accuracy figures.
3. **Forecast rows for times at or before their publish time are dropped**, since they are not forecasts.
4. **Missing hours are skipped, not filled.** Each screen shows how many hours were compared.
5. **Actuals are metered output.** When wind farms are curtailed, FUELHH records the lower figure, so the forecast can look too high on those days.
6. **The likely range (P10 to P90) is calculated from the same period it is drawn on.** With one month of data this is the practical option. In production it would come from earlier months.
7. **MAPE ignores hours under 1,000 MW**, where dividing by a small actual gives misleading percentages.
